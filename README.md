# Особистий Telegram-бот розкладу ЧНУ

Основа бота для групи **141, першої підгрупи**. Вимоги до повного розкладу описано у [SPEC.md](SPEC.md).

Реалізовано `/start`, `/help`, `/today`, `/tomorrow`, `/week`, `/next`, `/settings`, `/status`, нагадування перед парами, доступ лише для власника в особистому чаті, конфігурацію через `.env` і зберігання розкладу та налаштувань у SQLite. Розклад завантажується з локального Excel `.xls` кафедри МПУіК або JSON.

## Залежності

Використовуйте **Python 3.12**. Прямі залежності зафіксовано в `requirements.txt`: `aiogram==3.31.0`, `python-dotenv==1.2.4`, `xlrd==2.0.2`. `requirements.lock.txt` фіксує також усі встановлені транзитивні залежності для відтворення перевіреного середовища. SQLite та `asyncio` входять до стандартної бібліотеки Python. Залежності перевірено на Python 3.12; aiogram вимагає Python 3.10–3.14. Системний Python 3.9 не підходить.

Офіційні джерела, перевірені 04.10.2026:

- [aiogram: версія та вимоги Python](https://pypi.org/project/aiogram/)
- [aiogram: запуск через long polling](https://docs.aiogram.dev/en/latest/dispatcher/long_polling.html)
- [aiogram: middleware для перевірки доступу](https://docs.aiogram.dev/en/latest/dispatcher/middlewares.html)
- [python-dotenv: версія та завантаження .env](https://pypi.org/project/python-dotenv/)
- [xlrd: читання XLS і об’єднаних комірок](https://xlrd.readthedocs.io/en/latest/api.html)

## Локальний запуск

Виконуйте команди з кореня проєкту. Якщо Python 3.12 ще не встановлено, встановіть його з [python.org](https://www.python.org/downloads/).

```bash
python3.12 -m venv .venv
source .venv/bin/activate
python -m pip install -r requirements.lock.txt
cp .env.example .env
```

Створіть бота через офіційний [BotFather](https://t.me/BotFather), командою `/newbot`: задайте назву й унікальний username із закінченням `bot`. Збережіть отриманий токен лише у локальному `.env`. Інструкція Telegram: [BotFather](https://core.telegram.org/bots/features#botfather). У `.env` заповніть:

```dotenv
BOT_TOKEN=токен_від_BotFather
OWNER_TELEGRAM_ID=ваш_числовий_Telegram_ID
DATABASE_PATH=data/bot.sqlite3
TIMEZONE=Europe/Kyiv
SCHEDULE_SOURCE=data/schedule.xls
```

`OWNER_TELEGRAM_ID` — додатне число, а не `@username`. Це має бути ID вашого особистого Telegram-акаунта. Доступ не передається першому, хто напише боту: ID власника потрібно вказати заздалегідь.

Щоб отримати свій ID без стороннього бота, спочатку заповніть лише `BOT_TOKEN`, надішліть повідомлення своєму боту й виконайте:

```bash
python -m tgbot --show-user-ids
```

Основний бот має бути зупинений. Команда показує ID авторів приватних повідомлень, не надсилає відповіді й не надає доступ автоматично. Впишіть у `.env` саме свій ID.

| Змінна | Призначення |
| --- | --- |
| `BOT_TOKEN` | Обов’язковий секрет від BotFather |
| `OWNER_TELEGRAM_ID` | Обов’язковий числовий ID власника |
| `DATABASE_PATH` | Файл SQLite, стандартно `data/bot.sqlite3` |
| `SCHEDULE_SOURCE` | Локальний XLS для ручного оновлення, стандартно `data/schedule.xls` |
| `TIMEZONE` | `Europe/Kyiv`; інші значення відхиляються |

`.env` і локальні бази ігноруються Git. Токен не додавайте до README, SPEC або повідомлень у репозиторії. Змінні середовища мають пріоритет над `.env`. Відносний `DATABASE_PATH` рахується від кореня проєкту незалежно від робочої директорії.

Перевірте налаштування та створення SQLite без запиту до Telegram:

```bash
python -m tgbot --check
```

Запустіть бота:

```bash
python -m tgbot
```

Відкрийте свого бота в Telegram і надішліть `/start`, потім `/help`. `/start` зберігає особистий чат у базі. Повторний `/start` не скидає збережені налаштування. Сторонньому користувачу бот повідомляє про обмежений доступ, у групових чатах не відповідає.

Зупинка — `Ctrl+C`. Працювати має одна копія бота на один токен. Використовується long polling, публічна адреса та вебхук не потрібні. Якщо токен раніше використовувався з вебхуком, перед запуском видаліть той вебхук через Telegram Bot API.

Для постійної роботи узгоджено Linux/VPS із systemd; кроки наведено нижче. Фактичне розгортання потребує адреси й доступу до VPS. SQLite не потребує окремого сервера.

## Завантаження й перегляд розкладу

У поточному робочому каталозі вже активовано справжній розклад із наданого файлу. Його локальна копія — `data/schedule.xls`; файл і база ігноруються Git. На іншому комп’ютері потрібно надати власний файл і виконати імпорт. Якщо база порожня, команди повідомляють, що розклад ще не завантажено. Демонстраційні заняття не додаються автоматично.

### Оновлення з Excel

Узгоджене джерело — локальний файл `РОЗКЛАД (каф.МПУіК)_v13_09.xls` з аркушем `МПУіК` і підгрупою `141(1)`. Мережевий доступ, сайт чи університетський пароль для імпорту не потрібні. Формат перевіряється за вмістом файлу, а не лише розширенням; `.xlsx` цим імпортером не підтримується.

Перед активацією перегляньте обидва типи тижня без зміни SQLite:

```bash
python -m tgbot --preview-source
# Або: python -m tgbot --preview-source "шлях/до/нового.xls"
```

Перегляд використовує контрольні тижні 05–11 і 12–18.10.2026 та показує непідтверджений час і накладення. Для наступного семестру ці контрольні дати й особисті правила потрібно переглянути.

Щоб оновити з `SCHEDULE_SOURCE` у `.env` (стандартно `data/schedule.xls`):

```bash
python -m tgbot --update-source
```

Або вкажіть конкретний новий файл:

```bash
python -m tgbot --update-source "/абсолютний/шлях/до/нового розкладу.xls"
```

Імпорт та оновлення JSON працюють без Telegram-токена; для запуску самого бота токен і ID власника потрібні. Файл передавайте в цей чат із Codex при змінах: нову версію можна зберегти в `data/schedule.xls` або імпортувати за її шляхом. Для подальших оновлень без аргументу актуалізуйте `SCHEDULE_SOURCE`, якщо шлях змінився. Автоматичного завантаження нових розкладів із сайту немає.

Імпортер знаходить заголовок підгрупи, розбирає об’єднані комірки, щотижневі та окремі для двох типів тижня заняття. Зберігаються викладач, час, початкове позначення місця, окремі корпус і аудиторія, дати початку дії та посилання на комірки. Відсутні викладачі й аудиторії залишаються порожніми. Відсутній або некоректний час, заголовки, порожній розклад чи зміна структури блоків відхиляють оновлення.

Лише повністю прочитана та перевірена версія атомарно замінює активні заняття. Особливе правило ОНС зберігається окремо в календарній логіці; непідтверджений час не активує нагадування. Журнал відправок та налаштування власника при імпорті зберігаються. Імпорт повідомляє кількість доданих і вилучених записів. Нові записи ОНС, несумісні з відомим початковим форматом, відхиляються для уточнення особистого правила.

`/status` показує джерело, час останнього успішного оновлення в Києві та проблему останньої спроби, якщо вона була. Час оновлення також є у відповідях команд розкладу. Під час роботи бот раз на 60 секунд перевіряє доступність і SHA-256 активного XLS; `/status` перевіряє одразу. Зміна файлу позначає потребу в ручному оновленні, без автоматичної активації неперевірених даних.

Якщо файл недоступний, пошкоджений або має непідтримувану структуру, останній робочий розклад та час успішного оновлення залишаються незмінними. Відповіді й нагадування мають позначку **«Дані можуть бути застарілими»**. Помилка зберігається після перезапуску й очищується після успішного оновлення. Якщо джерело було недоступне, а потім відновилося, виконайте оновлення, щоб підтвердити актуальність. Бот перевіряє лише локальний файл; про нову університетську версію, яку ще не надано, він не може знати.

### Демонстраційні дані
Імпорт замінює попередній розклад у налаштованій SQLite. Для вигаданих даних використовуйте окрему базу для обох команд:

```bash
DATABASE_PATH=data/demo.sqlite3 python -m tgbot --import-schedule examples/demo_schedule.json
DATABASE_PATH=data/demo.sqlite3 python -m tgbot
```

Кожне повідомлення з демонстраційними заняттями містить **«ТЕСТОВИЙ РОЗКЛАД — вигадані дані»**, включно з усіма частинами довгого тижневого розкладу.

- `/today` — сьогоднішні пари.
- `/tomorrow` — завтрашні пари, включно з переходом на наступний тиждень.
- `/week` — поточний тиждень, понеділок–неділя.
- `/next` — найближча пара, початок якої ще попереду; пошук враховує майбутні дати початку дії розкладу.
- `/status` — джерело, останнє успішне оновлення та ознака можливої застарілості.

Дата визначається в `Europe/Kyiv`, незалежно від часового поясу сервера. Тип тижня перемикається щопонеділка від контрольної дати 05.10.2026 (парний). Заняття іншої групи чи підгрупи не показуються; спільні заняття групи включаються. Час, корпус, аудиторія та викладач показуються за наявності. Вихідні та порожні дні мають повідомлення «Цього дня пар немає».

### Формат JSON

Зразок — `examples/demo_schedule.json`. Верхній рівень містить рівно `source` (назва джерела), `is_demo` (boolean) і `lessons` (список занять). Для справжнього перевіреного розкладу вкажіть `is_demo: false`.

Обов’язкові поля заняття: `group` (рядок), `subgroup` (число або `null` для спільних занять), `weekday` (0–6, понеділок–неділя), `number` (1–7), `subject`, `start` і `end` (`HH:MM`). Додаткові: `week` (0 — щотижня, 1 — непарний, 2 — парний), `teacher`, `building`, `room`, `location`, `online`, `url`, `valid_from`, `valid_to` (`YYYY-MM-DD`, включно), `time_confirmed`, `source_cells`, `cancelled_dates` (список до 100 дат `YYYY-MM-DD`, у які заняття скасовано).

`location` зберігає початкове позначення місця, наприклад `8-216`; `building` і `room` — окремі поля корпусу й аудиторії. Не вигадуйте відсутні значення. Некоректні час, дати, поля та дублікати відхиляються до заміни даних; попередній розклад зберігається. Метадані джерела та час імпорту записуються разом із заняттями в одній транзакції.

Для справжнього розкладу застосовується особисте правило ОНС із SPEC: 16.10.2026 — онлайн, пари 4–6; 9 і 23 жовтня — звичайні заняття парного тижня. Старі записи ОНС не дублюються, за межами погодженого періоду не відновлюються. Час початку ОНС підтверджено користувачем: 13:00, 14:40 і 16:10; стандартні нагадування — о 12:50, 14:30 і 16:00. Посилання на заняття поки не надано. Інші предмети не скасовуються; накладення часу позначаються. Демонстраційний приклад не доповнюється справжнім правилом ОНС.

## Нагадування та налаштування

Після `/start` сповіщення стандартно ввімкнені за 10 хвилин до пари. Бот має бути запущений; без підключеного особистого чату або завантаженого розкладу надсилання не відбувається.

```text
/settings                 поточний стан та інструкція
/settings on              увімкнути сповіщення
/settings off             вимкнути сповіщення
/settings minutes 15      нагадувати за 15 хвилин
```

Інтервал — ціле число від 1 до 1440 хвилин. Вимкнення та зміна часу зберігаються після перезапуску й повторного `/start`. Налаштування застосовуються до наступної перевірки нагадувань.

Перевірка відбувається кожні 5 секунд без додаткових залежностей. Повідомлення містить дату, предмет, час, корпус і аудиторію або посилання на онлайн-заняття. Для відсутніх даних використовується відповідна позначка. Тестові нагадування явно позначені. Заняття з `time_confirmed: false` не запускають нагадування. Для ОНС час уже підтверджено, тому нагадування активні.

Перед кожною спробою бот читає актуальний розклад та налаштування, перевіряє їх версії й атомарно записує подію у `reminder_events`. Оновлення JSON не потребує перезапуску: видалені заняття та дати з `cancelled_dates` виключаються, перенесені пари й нові аудиторії враховуються. Зміна розкладу або налаштувань між читанням та резервуванням блокує застарілу спробу. Запит, уже переданий Telegram, відкликати неможливо.

Одне заняття ідентифікується датою, групою, номером пари, предметом і типом джерела (тестове/справжнє). Повторний імпорт, зміна часу нагадування, аудиторії або початку вже сповіщеного заняття не створюють друге нагадування для нього. Скасування окремої дати не прибирає заняття з інших тижнів; для повного скасування видаліть заняття з нового JSON.

Після перезапуску пропущене нагадування надсилається лише якщо його час уже настав, а сама пара ще не почалася. На початку пари та пізніше воно не надсилається. Хвилини рахуються за реальним часом UTC; календар і чергування тижнів — у `Europe/Kyiv`, включно з переходами літнього/зимового часу.

Журнал спроб зберігається між перезапусками й імпортами. Щоб уникнути повторів при втраті відповіді Telegram, спроба з невідомим результатом автоматично не повторюється. Через це повідомлення може бути пропущене при мережевій помилці або аварійному завершенні між резервуванням і підтвердженням відправки. Для явного обмеження частоти Telegram повтор дозволяється після `retry_after`, доки пара не почалася. Довідка про помилки — в [офіційній документації aiogram](https://docs.aiogram.dev/en/latest/dispatcher/errors.html).

```bash
python -m unittest discover -s tests -v

python scripts/check_repository.py
git diff --check
```

Тести використовують тимчасову SQLite та підроблену сесію Telegram, без реального токена й мережі. Вони перевіряють команди, доступ сторонніх користувачів і груп, збереження даних і налаштувань після перезапуску, міграцію старої бази, часові межі, чергування тижнів, зміни й скасування занять, конкурентні спроби відправки, мережеві помилки та переходи літнього/зимового часу.

## Постійна робота на Linux/VPS із systemd

Потрібні Python 3.12 із модулем `venv`, актуальна база часових поясів ОС, systemd та вихідний HTTPS-доступ до Telegram. Публічний домен і відкритий порт не потрібні. Команди нижче виконуються на VPS; шляхи служби фіксовані. Перевірте, що користувача `tgbot` ще немає, перед його створенням:

```bash
sudo useradd --system --home-dir /var/lib/tgbot --shell /usr/sbin/nologin tgbot
sudo install -d -o root -g root -m 755 /opt/tgbot
sudo install -d -o tgbot -g tgbot -m 700 /var/lib/tgbot
sudo install -d -o root -g tgbot -m 750 /etc/tgbot
```

Скопіюйте перевірений код у `/opt/tgbot` без `.env`, `.venv` і `data` або клонуйте власний репозиторій. Код має бути доступний користувачу `tgbot` для читання. Далі:

```bash
cd /opt/tgbot
sudo python3.12 -m venv .venv
sudo .venv/bin/python -m pip install -r requirements.lock.txt
sudo .venv/bin/python -m pip check
sudo install -o root -g tgbot -m 640 .env.example /etc/tgbot/bot.env
sudoedit /etc/tgbot/bot.env
```

У `/etc/tgbot/bot.env` заповніть токен і свій ID, а шляхи задайте так:

```dotenv
DATABASE_PATH=/var/lib/tgbot/bot.sqlite3
SCHEDULE_SOURCE=/var/lib/tgbot/schedule.xls
TIMEZONE=Europe/Kyiv
```

Передайте XLS на VPS приватно, наприклад через SFTP. Команда нижче очікує ваш файл `schedule.xls` у поточному каталозі; його не потрібно додавати до репозиторію:

```bash
sudo install -o tgbot -g tgbot -m 600 schedule.xls /var/lib/tgbot/schedule.xls
sudo -u tgbot env DATABASE_PATH=/var/lib/tgbot/bot.sqlite3 SCHEDULE_SOURCE=/var/lib/tgbot/schedule.xls /opt/tgbot/.venv/bin/python -m tgbot --preview-source
sudo -u tgbot env DATABASE_PATH=/var/lib/tgbot/bot.sqlite3 SCHEDULE_SOURCE=/var/lib/tgbot/schedule.xls /opt/tgbot/.venv/bin/python -m tgbot --update-source
sudo install -o root -g root -m 644 deploy/tgbot.service /etc/systemd/system/tgbot.service
sudo systemd-analyze verify /etc/systemd/system/tgbot.service
sudo systemctl daemon-reload
sudo systemctl enable --now tgbot.service
sudo systemctl status tgbot.service
sudo journalctl -u tgbot.service -n 50 --no-pager
```

Перед запуском служби зупиніть локальну копію. У Telegram виконайте `/start`, `/status`, `/settings` і перевірте найближче нагадування. `/start` необхідний для прив’язки приватного чату; знання ID саме по собі не дозволяє боту почати розмову.

Шаблон `deploy/tgbot.service` запускає бота від окремого користувача, перевіряє конфігурацію перед стартом, перезапускає процес після збою та дозволяє запис лише в `/var/lib/tgbot`. Збій фонової служби завершує процес, щоб systemd міг його відновити. Після 10 швидких невдалих запусків спрацює обмеження: виправте причину й виконайте `sudo systemctl reset-failed tgbot.service`, потім `sudo systemctl start tgbot.service`. Семантика перезапусків: [офіційна документація systemd](https://github.com/systemd/systemd/blob/main/man/systemd.service.xml).

На цьому Mac unit-файл не запускався: перевірка `systemd-analyze verify` та реальна доставка повідомлень мають відбутися на VPS. Після оновлення коду чи залежностей зупиніть службу, встановіть зафіксовані залежності та запустіть її знову. Зміна `bot.env` потребує перезапуску служби.

Для оновлення XLS замініть приватний файл і повторіть `--preview-source`, потім `--update-source` із серверними шляхами. Бот підхопить активовану SQLite без перезапуску. Сама заміна XLS лише позначає старі дані як потенційно застарілі.

Резервну копію `/var/lib/tgbot` робіть приватно при зупиненій службі, потім запустіть її знову. Зберігайте SQLite цілком, включно з журналом нагадувань: відновлення давньої копії може повторити події, надіслані після її створення. Токен із `/etc/tgbot/bot.env` зберігайте окремо з обмеженим доступом.

## Перед передачею в GitHub

`.gitignore` виключає `.env`, дані, бази, Excel-файли, приватні JSON, журнали та ключі. `scripts/check_repository.py` перевіряє відстежувані й нові неігноровані файли на приватні файли, токени, ID власника та особисті шляхи. Запускайте його перед кожним комітом; це локальна перевірка, а не гарантія від будь-якого витоку. Не обходьте виключення через `git add -f`.

Токени маскуються також у трасуваннях помилок. Не публікуйте журнали й резервні копії: вони можуть містити технічні подробиці або особистий розклад. Якщо токен було розкрито, перевипустіть його через BotFather та оновіть приватну конфігурацію.
